# 1.19 · Ollama en la práctica

Última sección del contenido. Acá el capítulo entero aterriza en comandos concretos sobre tu máquina.

**Ollama** envuelve `llama.cpp` y te da tres cosas: un registro de modelos ya cuantizados, un planificador que decide cuántas capas van a la GPU, y un servidor HTTP con API compatible con la de OpenAI — que es lo que hace que migrar `schema-rag` sea casi trivial.

---

## Los comandos que vas a usar

```bash
ollama pull  qwen2.5-coder:14b-instruct-q4_K_M   # descargar
ollama run   qwen2.5-coder:14b --verbose         # probar, mostrando tokens/s
ollama ps                                        # QUÉ ESTÁ CARGADO Y DÓNDE
ollama list                                      # qué tenés descargado
ollama stop  <modelo>                            # liberar VRAM
ollama serve                                     # levantar el servidor
```

**`ollama ps` es el más importante de los seis**, por lo que vimos en §1.18: su columna `Processor` te dice si estás en `100% GPU` o si silenciosamente estás repartiendo con la CPU. Es el chequeo de cinco segundos que evita horas de confusión.

`--verbose` te da los tokens por segundo, que es la otra métrica que necesitás para decidir si un modelo es usable.

---

## La configuración

Ollama se configura con variables de entorno. Éstas son las que importan:

| Variable | Qué hace | Default |
|---|---|---|
| `OLLAMA_CONTEXT_LENGTH` | Ventana de contexto | **4096** |
| `OLLAMA_KEEP_ALIVE` | Cuánto queda el modelo en memoria | 5m (`-1` = siempre) |
| `OLLAMA_MAX_LOADED_MODELS` | Modelos cargados a la vez | 3 × cantidad de GPUs |
| `CUDA_VISIBLE_DEVICES` | Qué GPU usar (NVIDIA) | todas |
| `ROCR_VISIBLE_DEVICES` | Ídem para AMD | todas |
| `GGML_VK_VISIBLE_DEVICES` | Ídem para Vulkan | — |
| `OLLAMA_VULKAN=0` | Desactiva Vulkan | — |

Para forzar CPU pura se pasa un ID de GPU inválido, por ejemplo `-1`.

Tres cosas de esa tabla que causan sorpresas:

**El default de contexto son 4.096 tokens**, no lo que dice la ficha del modelo. Mucha gente cree que está usando la ventana de 128K de un modelo y está usando 4K. La ventana se puede fijar de tres formas:

```bash
OLLAMA_CONTEXT_LENGTH=8192 ollama serve      # por servidor
```
```
/set parameter num_ctx 8192                   # por sesión, en la CLI
```
```json
{"options": {"num_ctx": 8192}}                // por pedido, en la API
```

**Los modelos quedan cargados 5 minutos** después del último uso. Si estás probando varios seguidos, podés tener dos o tres comiéndose la VRAM sin darte cuenta. `ollama ps` te lo muestra; `ollama stop` los baja.

**Si no hay memoria para cargar un modelo nuevo** mientras otros están en uso, los pedidos nuevos **se encolan** hasta que se pueda cargar, y los modelos ociosos se van descargando para hacer lugar. No falla: espera. Que es otra forma de "anda lento sin decir por qué".

## Migrar schema-rag: es casi copiar y pegar

Ollama expone un endpoint compatible con la API de OpenAI, así que el cambio en tu código es mínimo:

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama",                       # ignorada, pero el SDK la exige
)

r = client.chat.completions.create(
    model="qwen2.5-coder:14b-instruct-q4_K_M",
    messages=[...],
    temperature=0,                          # §1.8
    max_tokens=1200,                        # §1.10
    extra_body={"options": {"num_ctx": 8192}},
)
```

Los parámetros por pedido que ya conocés: `temperature`, `top_p`, `top_k` (que acá sí está disponible, a diferencia de las APIs comerciales), `seed`, `num_ctx`, y `num_predict` — que es el equivalente local de `max_tokens`.

## Dónde Ollama se queda corto

Vale la pena saberlo para no descubrirlo tarde. **Ollama es cómodo pero opaco**: toma decisiones por vos, como cuántas capas manda a la GPU o qué cuantización trae un tag sin sufijo. Para experimentar y para un usuario, es ideal.

Tres casos donde vas a necesitar otra cosa:

**Concurrencia y throughput.** Si algún día tenés que servir a varios usuarios en paralelo con buen rendimiento, vas a mirar **vLLM**. Es material de la materia de producción (M6).

**Constrained decoding con gramáticas finas.** Para el nivel 4 de §1.13 vas a querer `outlines` sobre `transformers`, o las gramáticas GBNF de `llama.cpp` directo. Ollama no te expone eso con la comodidad que necesitás.

**Control fino de cuantización.** Si querés cuantizar un modelo vos mismo con un conjunto de calibración de tu dominio —lo de §1.16— eso es `transformers` con `BitsAndBytesConfig`, no Ollama.

---

## Cómo se ve esto en schema-rag: el plan completo

Cinco pasos, en orden, sin saltear:

**1. Verificá el driver.** `nvidia-smi` te muestra la versión en la esquina superior. Necesitás **550 o superior** (§1.18).

**2. Bajá un modelo chico primero.** Un 7B–8B cuantizado a Q4. Corré `ollama ps` y **confirmá que dice `100% GPU`**. Si dice otra cosa, resolvelo antes de seguir: no tiene sentido evaluar calidad sobre un sistema mal configurado.

**3. Encontrá tu `num_ctx` máximo.** El experimento de §1.18: subí de a poco hasta que `ollama ps` deje de decir `100% GPU`. **Ese número es tu presupuesto real de contexto.**

**4. Recién ahí probá un modelo más grande.** Con el presupuesto medido, ya sabés qué podés pedirle a los 16 GB.

**5. Corré el torneo.** Tus 20 preguntas, el mismo esquema pydantic, contra cada candidato y contra tu API actual. La tabla de §1.17.

Al final de eso, si el modelo local te da 100 % de JSON parseable y una tasa de queries correctas aceptable, **tenés una versión de `schema-rag` donde `CLIENTENRO` nunca sale de tu red**. Que era el objetivo de toda la Parte V.

Y si no llega, tenés algo casi igual de valioso: **el número exacto de cuánto te falta**, que es lo que te permite decidir con criterio en vez de con impresión.

## Errores frecuentes

**No mirar nunca `ollama ps`.** Lo repito a propósito: es el chequeo que más problemas evita.

**Creer que usás el contexto completo del modelo.** El default son 4.096.

**Dejar modelos cargados.** Pueden ser hasta tres comiéndose la VRAM.

**Usar un tag sin sufijo de cuantización.** `modelo:14b` te da la cuantización por defecto, que puede cambiar entre versiones. Sé explícito: `modelo:14b-instruct-q4_K_M`.

**Evaluar calidad sin haber verificado que corre 100 % en GPU.** Vas a estar midiendo una configuración rota.

**Comparar contra tu API con distinta configuración.** Mismo prompt, mismo esquema, misma temperatura, mismas preguntas. Si no, no es comparación.

## Resumen de la sección

1. Ollama = registro de modelos + planificador de GPU + servidor compatible con la API de OpenAI.
2. **`ollama ps`** es el comando clave: la columna `Processor` te dice si estás en `100% GPU`.
3. `--verbose` te da los **tokens por segundo**.
4. El **default de contexto son 4.096 tokens**, y se configura por servidor, por sesión o por pedido.
5. Los modelos quedan cargados **5 minutos**, y puede haber **hasta 3** simultáneos ocupando VRAM.
6. Migrar `schema-rag` es cambiar `base_url`: la API es compatible.
7. Ollama es cómodo y **opaco**. Para concurrencia, mirá vLLM; para gramáticas, `outlines` o `llama.cpp`.
8. El plan: **driver → modelo chico → medir `num_ctx` → modelo grande → torneo.**
