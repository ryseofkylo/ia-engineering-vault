# 1.17 · Elegir un modelo

Ya sabés qué significa cuantizar y cómo funciona. Esta sección es la aplicación: **cómo se lee la ficha de un modelo, y cómo se decide cuál bajar** sin depender de rankings que no miden tu tarea.

---

## Leer un nombre de archivo

Ésta es la habilidad concreta que te llevás. Dos ejemplos, uno de cada ecosistema.

### En el mundo Hugging Face

```
Qwen2.5-Coder-14B-Instruct-GPTQ-Int4
│        │     │   │        │    └── 4 bits por peso → ~7 GB de pesos
│        │     │   │        └─────── método de PTQ que compensa el error capa por capa
│        │     │   └──────────────── afinado para seguir instrucciones
│        │     └──────────────────── 14.000 millones de parámetros
│        └────────────────────────── especializado en código
└─────────────────────────────────── familia y versión
```

Si además aparece un `128g`, es el tamaño de grupo de §1.16.

### En el mundo GGUF, que es el que vas a ver en Ollama

```
modelo-Q4_K_M.gguf
       │ │ │
       │ │ └── M = medium: cuánto se cuida la calidad dentro del esquema
       │ └──── K = k-quants: cuantización por bloques, con escalas por bloque
       └────── 4 bits por peso
```

**`Q4_K_M` es el default de facto de la comunidad**: 4 bits, por bloques, calidad media. Y "por bloques" es exactamente la granularidad *per-group* de §1.16, con otro nombre.

Ese sufijo `_K_M` **no es cosmético**. Un `Q4_0` (sin k-quants) y un `Q4_K_M` son los dos "4 bits" y no son comparables.

---

## El dilema del presupuesto fijo, resuelto

Retomemos el planteo de §1.15. Con 16 GB, estas opciones ocupan lo mismo:

| Opción | VRAM aproximada |
|---|---|
| Modelo de código 7B a Q8 | ~8 GB |
| Modelo de código 14B a Q4_K_M | ~8 GB |
| `gpt-oss:20b` (MXFP4) | ~14 GB |
| Modelo generalista 30B a Q3 | ~14 GB |

La regla general dice: **el modelo grande cuantizado le gana al chico completo.** Y está bien fundada — para chat y para tareas de lenguaje general, donde importa el conocimiento amplio y la fluidez, y donde ningún nivel de precisión numérica compensa conocimiento que no está.

> **Pero esa regla se apoya en tareas que no son la tuya.**
>
> Text-to-SQL no es chat. Es **generación de código con gramática estricta**, donde importa la precisión sintáctica y seguir un esquema al pie de la letra. Es plausible —y hay que medirlo— que en tu caso un modelo **especializado en código** de 14B a Q5 le gane a un generalista de 30B a Q3. La especialización del entrenamiento puede pesar más que el tamaño.

O sea: usá la regla como **punto de partida**, no como conclusión.

Y hay dos factores más que la regla ignora y que a vos te importan:

**El contexto.** Un modelo que ocupa 15 de tus 16 GB no te deja lugar para el KV cache, y vas a terminar con una ventana de 2.048 tokens. Para un sistema RAG sobre un esquema de 14.232 columnas, eso puede ser peor que un modelo más chico con contexto amplio. Esto lo cuantificamos en §1.18.

**La velocidad.** Un modelo que da 8 tokens por segundo puede ser inutilizable en la práctica, aunque acierte más.

---

## El torneo: cómo se decide de verdad

La forma correcta de elegir no es leer comparativas. Es correr un torneo con tus datos.

Las mismas 20 preguntas del trabajo práctico contra cada candidato, y esta tabla:

| Modelo | % JSON parseable | % queries que compilan | % correctas | tokens/s | VRAM libre |
|---|---|---|---|---|---|
| Código 7B a Q8 | | | | | |
| Código 14B a Q4_K_M | | | | | |
| `gpt-oss:20b` | | | | | |
| Generalista 30B a Q3 | | | | | |
| *(Tu API actual, de referencia)* | | | | | |

Esa tabla, completada con tus números, **vale más que cualquier ranking que leas**. Y la última fila es importante: te dice cuánto estás resignando, si es que resignás algo.

Las cuatro columnas de calidad miden cosas distintas y conviene no colapsarlas:

- **% JSON parseable** — el criterio del trabajo práctico. Formato.
- **% que compilan** — validez sintáctica del SQL contra la base. Es la que más te va a sorprender.
- **% correctas** — que devuelvan el resultado esperado. La que de verdad importa, y la más cara de medir.
- **tokens/s** y **VRAM libre** — si el sistema es usable.

## Criterios antes de descargar

Antes de bajar 14 GB, cinco chequeos de dos minutos:

**1. Leé la licencia.** Está en la página del modelo, en la solapa de archivos. Ver §1.14: descargable no es lo mismo que comercialmente usable.

**2. Mirá quién lo publicó y si lo mantiene.** Un modelo abandonado no recibe correcciones. En Ollama, preferí los del registro oficial; en Hugging Face, publicadores conocidos.

**3. Confirmá que existe en el formato que necesitás.** Para Ollama, GGUF cuantizado.

**4. Hacé la cuenta de VRAM.** `parámetros × bytes_por_parámetro`, más el KV cache de §1.18. Antes de descargar, no después.

**5. Anotá la versión exacta.** `qwen2.5-coder:14b-instruct-q4_K_M`, no "el Qwen". Y en Ollama, **sé explícito con el sufijo de cuantización**: un tag sin sufijo te da la cuantización por defecto, que puede cambiar.

---

## Los dos ecosistemas que vas a usar

Conviene saber cuándo usar cada uno, porque no son intercambiables.

**Ollama** — el camino corto. Registro de modelos, descarga con un comando, servidor con API compatible con OpenAI, decisiones automáticas de cuántas capas van a la GPU. Es lo que vas a usar para probar y para servir. Detalles en §1.19.

**Hugging Face Hub + `transformers`** — el camino con control. El Hub es donde viven los modelos con sus fichas, licencias y archivos. `transformers` te da control fino: qué precisión, qué dispositivo, qué backend de cuantización (bitsandbytes, torchao, compressed-tensors, todos unificados detrás de la misma API), y —esto es lo importante— **acceso directo a los logits**.

La regla: **Ollama para probar rápido; `transformers` cuando necesites los logits.** Y necesitás los logits para constrained decoding (§1.13), o sea para la garantía de formato más fuerte que existe.

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

model_id = "meta-llama/Llama-3.1-8B-Instruct"

model = AutoModelForCausalLM.from_pretrained(
    model_id,
    quantization_config=BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_compute_dtype=torch.bfloat16,
    ),
    dtype=torch.bfloat16,
    device_map="auto",
)
tok = AutoTokenizer.from_pretrained(model_id)
```

Dos advertencias sobre ese código:

**`device_map="auto"` reparte capas entre GPU y CPU automáticamente.** Cómodo, pero **puede hacer offload sin avisarte** y dejarte el sistema lentísimo en silencio. Verificá con `nvidia-smi` que quedó todo en GPU. Es el mismo problema que vemos en §1.18.

**Usá `apply_chat_template` para armar los prompts**, no strings a mano. Ya lo vimos en §1.3: cada modelo abierto tiene su propio formato de turnos y sus propios tokens especiales.

## Cómo se ve esto en schema-rag

Tu punto de partida razonable, con lo que sabemos hasta acá:

- **Un modelo especializado en código, de 7B a 14B, en Q4_K_M.** Entra cómodo, deja lugar para contexto, y la especialización probablemente compense el tamaño para tu tarea.
- **`gpt-oss:20b` como el candidato "grande"**, porque es el único con dato de fuente primaria sobre correr en 16 GB.
- **Tu API actual como línea de referencia**, para saber cuánto estás resignando.

Y el criterio de aprobación no es ganarle a nadie: es **pasar tu evaluación**, con los números de tu propia tabla.

---

## Errores frecuentes

**Elegir por leaderboard.** Miden tareas generales; la tuya es específica.

**Aplicar la regla del "grande cuantizado" sin medir en tu tarea.**

**Olvidar el contexto en la cuenta.** Un modelo que llena la VRAM te deja sin ventana.

**Ignorar la velocidad.** La calidad no sirve si el sistema es inusable.

**Ignorar el sufijo `_K_M` o el `128g`.** No son cosméticos.

**Usar un tag sin sufijo de cuantización.**

**Creerle a un blog sobre "los mejores modelos para 16 GB".** Ese espacio está lleno de contenido de afiliados que se contradice.

**Confiar en `device_map="auto"` sin verificar.**

---

## Resumen de la sección

1. Un nombre de modelo se lee: familia, especialización, **parámetros**, ajuste, **método de cuantización**, **bits** y **granularidad**.
2. En GGUF, **`Q4_K_M`** es el default de facto: 4 bits, k-quants por bloques, calidad media. El sufijo no es cosmético.
3. La regla "**grande cuantizado le gana a chico completo**" vale para chat; **text-to-SQL no es chat**, y la especialización en código puede pesar más.
4. La regla ignora dos cosas que a vos te importan: **cuánta VRAM queda para el contexto** y **la velocidad**.
5. La decisión se toma con un **torneo** sobre tus 20 preguntas, no con comparativas ajenas.
6. Antes de descargar: **licencia, publicador, formato, cuenta de VRAM y versión exacta**.
7. **Ollama para probar; `transformers` cuando necesites los logits.**
