# 1.20 · Trabajo práctico

> **El enunciado.** Forzás salida estructurada en tu RAG de `schema-rag`: el LLM devuelve SQL + explicación como JSON validable con pydantic, no texto libre.
> **Se aprueba cuando:** 20 pedidos de "generame la query para X" devuelven JSON parseable el **100 %** de las veces, **sin reintentos**.

Todo lo que hace falta para resolverlo está en §1.11, §1.12 y §1.13. Esta sección lo pone junto y agrega el procedimiento.

---

## Por qué este trabajo práctico y no otro

Porque es el punto donde el LLM deja de ser un chat y pasa a ser un componente de software.

Un componente de software tiene un contrato: entra esto, sale esto con esta forma. Mientras `schema-rag` devuelva texto libre que después parseás con expresiones regulares, no tenés un componente: tenés una apuesta que gana el 90 % de las veces.

El **"sin reintentos"** del criterio está puesto a propósito. Reintentar es tapar el problema y pagarlo — §1.12 tiene la cuenta.

---

## Paso 1 · El esquema

```python
from pydantic import BaseModel, Field, field_validator

class RespuestaSQL(BaseModel):
    sql: str = Field(
        description="La consulta T-SQL que responde la pregunta. "
                    "Sin markdown, sin backticks, sin punto y coma final."
    )
    explicacion: str = Field(
        description="Qué hace la query, en una sola oración, en español."
    )
    tablas_usadas: list[str] = Field(
        description="Nombres exactos de las tablas referenciadas, con esquema. "
                    "Ej: dbo.Contratos"
    )

    @field_validator("sql")
    @classmethod
    def sin_markdown(cls, v: str) -> str:
        if "```" in v:
            raise ValueError("El SQL no debe venir dentro de un bloque de markdown")
        return v.strip().rstrip(";")

    @field_validator("sql")
    @classmethod
    def solo_lectura(cls, v: str) -> str:
        prohibidos = ("DROP ", "DELETE ", "UPDATE ", "INSERT ",
                      "TRUNCATE ", "ALTER ", "EXEC ")
        if any(p in v.upper() for p in prohibidos):
            raise ValueError("Sólo se permiten consultas de lectura")
        return v
```

Las tres decisiones de diseño, por si tenés que defenderlas:

- **Plano, sin anidar** (§1.11): la estructura profunda degrada la calidad del contenido.
- **Las `description` son prompt** (§1.11), no documentación.
- **`tablas_usadas` es un mecanismo de verificación** (§1.7), no un campo decorativo: lo contrastás contra `INFORMATION_SCHEMA` sin ejecutar la query.
- **`solo_lectura` es un control de seguridad** (§1.12) en el borde entre el LLM y tu base.

## Paso 2 · La generación

```python
import json
from openai import OpenAI

client = OpenAI()

def generar(pregunta: str, fragmentos: list[str]) -> tuple[RespuestaSQL, dict]:
    r = client.chat.completions.create(
        model=MODELO,                     # versión exacta, no un alias  (§1.7)
        messages=[
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": armar_prompt(pregunta, fragmentos)},
        ],
        temperature=0,                    # text-to-SQL es determinístico (§1.8)
        max_tokens=1200,                  # con margen: el truncado parece
                                          # error de formato (§1.10)
        tools=[{
            "type": "function",
            "function": {
                "name": "devolver_sql",
                "description": "Devuelve la consulta T-SQL que responde la pregunta",
                "parameters": RespuestaSQL.model_json_schema(),
            },
        }],
        tool_choice={"type": "function", "function": {"name": "devolver_sql"}},
    )

    meta = {
        "finish_reason": r.choices[0].finish_reason,
        "tokens_in": r.usage.prompt_tokens,
        "tokens_out": r.usage.completion_tokens,
    }
    crudo = r.choices[0].message.tool_calls[0].function.arguments
    return RespuestaSQL(**json.loads(crudo)), meta | {"crudo": crudo}
```

Cada decisión de ese bloque tiene una sección detrás. **Sin `meta` no podés analizar los fallos**, así que no lo saltees.

Y aprovechá para aplicar lo de la Parte II al armar el prompt (§1.6): el fragmento más relevante primero, el segundo último.

## Paso 3 · La medición

```python
import json
from pydantic import ValidationError

def evaluar(preguntas: list[str]) -> dict:
    resultados = []
    for p in preguntas:
        fragmentos = recuperar(p)
        try:
            respuesta, meta = generar(p, fragmentos)
            resultados.append({"pregunta": p, "ok": True, **meta,
                               "sql": respuesta.sql,
                               "tablas": respuesta.tablas_usadas})
        except (ValidationError, json.JSONDecodeError) as e:
            resultados.append({"pregunta": p, "ok": False, "error": str(e)})

    ok = sum(r["ok"] for r in resultados)
    print(f"JSON parseable: {ok}/{len(preguntas)} = {ok/len(preguntas):.0%}")
    return {"resultados": resultados, "tasa": ok / len(preguntas)}
```

**Guardá los resultados en un archivo.** No los mires por consola y los tires: son tu primer conjunto de evaluación y los vas a reusar en cada capítulo que sigue.

## Las 20 preguntas

Elegilas **antes** de escribir código, no después de ver qué anda.

| Cantidad | Tipo | Por qué |
|---|---|---|
| 6 | Simples: una tabla, un filtro | El piso |
| 6 | Con JOIN de 2–3 tablas | El caso real |
| 4 | Con agregación (`GROUP BY`, `COUNT`, `SUM`) | Donde se complica |
| 2 | Con ambigüedad entre tablas de nombre parecido | El caso feo |
| 2 | **Imposibles**: piden datos que no existen en el esquema | **El modelo debería decirlo, no inventar** |

Las dos últimas son las más informativas. **Un sistema que inventa una respuesta para una pregunta imposible es peor que uno que dice que no puede** — y eso conecta directo con la alucinación de §1.7.

> **El criterio es sobre parseo, no sobre corrección.** Las 20 tienen que devolver JSON parseable. Que las queries sean **correctas** es otra medición, y es material de la materia M3. Contá los dos números por separado, en la misma corrida, y no los mezcles.

---

## Qué hacer cuando no llega al 100 %

En este orden. **No saltees pasos**, sobre todo el primero:

1. **Mirá `finish_reason`.** Si dice `length`, es truncado: subí `max_tokens`. **Es el caso más frecuente y el peor diagnosticado** (§1.10).
2. **Mirá la salida cruda** de los fallos. ¿Faltaba un campo? ¿El tipo era otro? ¿Fue un validador tuyo?
3. **Simplificá el esquema.** Si `tablas_usadas` es lo que falla, probá con dos campos y agregá el tercero después.
4. **Mejorá las `description`.** Son prompt.
5. **Recién ahí**, considerá subir al nivel 4: constrained decoding con un modelo local (§1.13 y §1.19).

Lo que **no** hay que hacer: agregar reintentos y declarar victoria. El criterio dice "sin reintentos" justamente para cerrar esa salida.

## Extensiones, después de aprobar

- **Verificación de alucinación.** Contrastá `tablas_usadas` contra `INFORMATION_SCHEMA` y contá cuántas veces el modelo nombra tablas inexistentes (§1.7).
- **Ejecución en seco.** `SET NOEXEC ON` y contá cuántas queries compilan. Ese número es más informativo que el del trabajo práctico.
- **Los tres baselines.** Closed-book, sistema real y oracle sobre las mismas 20 (§1.5 y §1.6).
- **Varias candidatas.** Generá 3 con `top_p=0.8` y quedate con la que compila (§1.10).
- **Versión local.** Repetí todo contra un modelo en Ollama y compará (§1.19).
