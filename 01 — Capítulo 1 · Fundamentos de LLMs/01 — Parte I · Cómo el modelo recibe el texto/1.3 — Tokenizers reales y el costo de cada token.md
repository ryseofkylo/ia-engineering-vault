# 1.3 · Tokenizers reales y el costo de cada token

Hasta acá vimos cómo se construye un tokenizer en abstracto. Esta sección baja a tierra: cuáles son las dos implementaciones que te vas a cruzar en la práctica, cuánto te sale cada token en plata, y el catálogo completo de comportamientos raros del modelo que se explican por la tokenización.

Es la sección más "operativa" de la Parte I. Lo de acá se convierte directamente en líneas de código y en decisiones de presupuesto.

---

## Las dos familias de tokenizer

Hay dos enfoques dominantes, y la diferencia entre ellos importa el día que pases de una API comercial a un modelo abierto corriendo en tu máquina.

### tiktoken — el enfoque de OpenAI

El orden de operaciones es: texto → code points Unicode → **bytes UTF-8** → BPE sobre bytes.

Es decir: todo carácter termina descompuesto en bytes **antes** de cualquier fusión. Es uniforme, sin casos especiales, sin configuración. La librería `tiktoken` codifica y decodifica; no entrena tokenizers nuevos.

Un apunte histórico que sirve si alguna vez te topás con código viejo: antes de `tiktoken`, OpenAI había publicado el tokenizer de GPT-2 como un archivo suelto llamado **`encoder.py`**, con su vocabulario y su lista de fusiones en dos archivos JSON aparte. Hace exactamente lo mismo que vimos en §1.2 —regex de pre-tokenización, después las fusiones en orden— sólo que escrito a mano y sin optimizar. `tiktoken` es su reemplazo moderno: misma lógica, implementación rápida en Rust.

### SentencePiece — el enfoque de Llama y buena parte del mundo abierto

El orden es distinto: texto → **code points Unicode** → BPE sobre code points, **con byte fallback** para los caracteres raros.

O sea: las fusiones a nivel carácter ocurren **antes** de descomponer a bytes, y sólo se cae a bytes para lo que no está cubierto. Llama 2, por ejemplo, se configura con `character_coverage=0.99995` y `byte_fallback=true`: cubre el 99,995 % de los caracteres del corpus directamente como caracteres, y el resto lo resuelve por bytes.

### La diferencia práctica

SentencePiece tiende a ser **más eficiente para idiomas que no son inglés**, porque las fusiones a nivel carácter capturan unidades con sentido lingüístico. El enfoque puramente de bytes de tiktoken necesita secuencias más largas para escrituras complejas.

A cambio, SentencePiece arrastra muchas opciones de configuración y bastantes rarezas históricas; tiktoken es más simple pero más limitado.

### La consecuencia que te va a morder

**El mismo prompt cuenta distinta cantidad de tokens según el tokenizer.**

```python
# API de OpenAI
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
n_openai = len(enc.encode(prompt))

# Modelo abierto, con el tokenizer que le corresponde
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")
n_llama = len(tok.encode(prompt))

print(n_openai, n_llama)   # rara vez coinciden
```

Si presupuestás la ventana de `schema-rag` con `cl100k_base` y después servís con un modelo local, **tu presupuesto está mal**. Hay que recontar con el tokenizer del modelo que realmente vas a usar. Volvemos sobre esto en §1.18, cuando calculemos cuánto entra en tu GPU.

Hay un detalle asociado que provoca degradaciones silenciosas: cada modelo abierto tiene su **propio formato de turnos de chat**, con sus propios tokens especiales. Armar ese string a mano es una fuente clásica de que el modelo rinda peor sin motivo aparente. La forma correcta es pedírselo al tokenizer:

```python
mensajes = tok.apply_chat_template(
    [{"role": "user", "content": pregunta}],
    tokenize=False, add_generation_prompt=True,
)
```

## El costo, en plata

Las APIs cobran **por token**, y cobran distinto la entrada que la salida. La salida siempre es más cara: típicamente entre tres y cinco veces.

```
costo = (tokens_entrada × precio_entrada) + (tokens_salida × precio_salida)
```

En un sistema RAG como `schema-rag`, la entrada domina por lejos: mandás un system prompt largo más *k* fragmentos de esquema, y recibís una query corta. **La palanca de costo está casi toda del lado de la entrada**, que es justamente donde el tokenizer te penaliza por escribir en español con identificadores raros.

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

PRECIO_IN  = 3.00 / 1_000_000    # poné acá los precios reales de tu proveedor
PRECIO_OUT = 15.00 / 1_000_000

def costo(prompt, salida_estimada=300):
    t_in = len(enc.encode(prompt))
    return t_in * PRECIO_IN + salida_estimada * PRECIO_OUT, t_in
```

**Logueá `t_in` en cada llamada.** En una semana vas a tener la distribución real de tu consumo, que casi nunca es la que uno cree. Y a diferencia de casi todo lo demás en este capítulo, esto es medible antes de gastar: contar tokens es una línea de código; descubrir el costo en la factura del mes es tarde.

Dos mecanismos cambian la cuenta y conviene tenerlos en el radar:

**Prompt caching.** Si la parte fija de tu prompt no cambia entre llamadas, varios proveedores la cobran bastante más barata. Es el tema principal de la materia siguiente (M2).

**El costo local.** Con un modelo propio no pagás por token, pero pagás en VRAM ocupada y en tokens por segundo. El presupuesto sigue existiendo: cambia de moneda. Toda la Parte V trata sobre esa otra moneda.

Y una trampa que aparece siempre en chats: **cada turno reenvía todo el historial anterior**, así que el costo de una conversación crece de forma cuadrática con su largo. En `schema-rag` esto no aplica hoy, pero va a aplicar apenas le agregues memoria.

## El catálogo de rarezas

Acá está la parte entretenida. Todas estas conductas del modelo parecen defectos misteriosos y tienen la misma causa: cómo se partió el texto.

Vale la pena leerlas juntas, porque el patrón es el que importa. Cuando algo raro pase, la primera hipótesis no debería ser "el modelo es tonto" ni "necesito un prompt mejor", sino **"¿cómo se tokenizó esto?"** — y esa hipótesis se verifica en dos líneas de código.

**No sabe deletrear.** Ya lo vimos en §1.1: ve `[ferro, carril]`, no letras. Contar caracteres es inferencia estadística, no lectura.

**Se equivoca en aritmética.** Los números se parten de forma inconsistente: `127` puede ser un token y `677` dos. El modelo no puede alinear unidades con decenas si no las ve separadas de manera regular. **Corolario: la cuenta la hace tu código o la base de datos, nunca el LLM.**

**Se rompe con la indentación de Python.** GPT-2 tokenizaba mal las secuencias de espacios y por eso era notoriamente malo con Python. GPT-4 mejoró la regex de pre-tokenización justamente para esto.

**Un espacio al final del prompt lo degrada.** Si tu prompt termina en `" "`, ese espacio se tokeniza como un token suelto en lugar de fusionarse con la primera palabra que el modelo iba a generar. El modelo queda en un estado que casi no vio durante el entrenamiento, y la calidad cae. Es una de las causas más comunes de degradación silenciosa, y se arregla con un `.rstrip()`.

**Los idiomas que no son inglés cuestan más.** Menos fusiones aprendidas = más tokens por la misma idea = más plata y más ventana consumida.

**JSON cuesta más que YAML.** JSON está lleno de comillas, llaves y dos puntos, y cada uno de esos símbolos tiende a ser su propio token. YAML expresa lo mismo con menos tokens. Si tenés que mandar mucha estructura *dentro* del prompt, YAML puede ahorrarte bastante. (Ojo: esto es sobre lo que le mandás. Lo que el modelo **devuelve** es otro tema, y ahí JSON gana por otras razones, que vemos en la Parte IV.)

**`SolidGoldMagikarp` y los glitch tokens.** Éste es el más raro y el más instructivo. Hay tokens que existen en el vocabulario porque aparecían en el corpus del **tokenizer**, pero que casi no aparecieron en el corpus del **modelo**. Su representación interna quedó prácticamente sin entrenar, y el modelo hace cosas erráticas cuando los encuentra: los ignora, responde otra cosa, o directamente delira. Es la consecuencia directa de que tokenizer y modelo se entrenen por separado, que vimos en §1.2.

## Cómo se ve esto en schema-rag

Tres acciones concretas, todas de hoy:

**Medí tu ratio.** Contá los tokens de un `CREATE TABLE` real y dividí caracteres sobre tokens. Ese número —caracteres por token— es tu presupuesto real. La referencia de ~4 que circula por internet es para inglés; el tuyo va a ser peor, y saber cuánto peor cambia todos tus cálculos.

**Limpiá los bordes del prompt.** Que ningún prompt termine en espacio ni en salto de línea suelto. Es un `.rstrip()` y elimina una fuente entera de degradación.

**Sacale la aritmética al modelo.** Cualquier conteo, suma o comparación numérica se hace en SQL, no en el prompt.

Y una decisión de arquitectura para tener en cuenta: si algún día evaluás mandar el esquema como estructura en lugar de como DDL, probá YAML antes que JSON. Mismo contenido, menos tokens, más lugar para fragmentos.

## Errores frecuentes

**Usar `cl100k_base` para estimar el costo o el largo de cualquier modelo.** Sirve para GPT-4 y poco más.

**Creer que `tiktoken` entrena tokenizers.** Sólo codifica y decodifica. Para entrenar están `minbpe`, SentencePiece o la librería `tokenizers` de Hugging Face.

**Estimar por "caracteres dividido cuatro".** Es una regla para inglés y te miente en español y en identificadores técnicos.

**Armar el prompt de chat de un modelo abierto a mano** en lugar de usar `apply_chat_template`.

**Intentar arreglar con prompt engineering un problema de tokenización.** No se arregla desde el prompt: el problema está antes de que el prompt llegue al modelo.

---

## Resumen de la sección

1. **tiktoken** trabaja siempre sobre bytes; **SentencePiece** trabaja primero sobre caracteres y cae a bytes sólo para los raros. SentencePiece suele ser más eficiente fuera del inglés.
2. El mismo texto **cuenta distinto** según el tokenizer. Si vas a servir con un modelo local, recontá con su tokenizer.
3. La salida cuesta entre 3 y 5 veces más que la entrada, pero en RAG **la entrada domina el costo total**.
4. Contar tokens antes de mandar es una línea de código; conviene loguearlo siempre.
5. Deletreo, aritmética, indentación, espacios finales, idiomas, JSON vs YAML y los glitch tokens **tienen todos la misma causa**: cómo se partió el texto.
6. Ante un comportamiento raro, la primera hipótesis es la tokenización, y se verifica en dos líneas.
